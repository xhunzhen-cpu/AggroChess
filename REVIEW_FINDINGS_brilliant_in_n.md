# Review findings (full list)

Archived from a 10-lens adversarial review of the "brilliant in N" design, each finding
checked against source. The blockers all match what running the implementation showed.
The workflow's own transcripts were deleted after the work was finished; this file is the
permanent record.

## [BLOCKER] The no-regret test is applied only to declining replies; the replies the opponent will actually choose are unbounded (Tier 1 is unbounded entirely)
- **Where:** `DESIGN_brilliant_in_n.md:31-50,68-69 (Tier 1/2 predicates) vs src/search.rs:2439-2490`
- **Claim:** The design's guard is `min over DECLINING R' >= value(normal best move) - 20`, but the opponent picks whichever reply minimises our value, and an ALLOWING reply is not constrained by anything except the single-reply verification of B; Tier 1 has no score bound at all, yet it is called FORCED. This is exactly the criterion the design's own 'user's verbatim intent' (DESIGN:18-22) says must block the move: 'if they can make the position worse don't do it'.
- **Failure:** Objective root score +120. S is a quiet setup. After S the opponent has R1 (allowing): our value there is +20, because R1 develops against the setup; and R2 (declining): +105. Static scan: candidates(after S,R1) non-empty, candidates(after S,R2) empty, so R2 is a decliner. Tier 2 needs min over decliners >= 120-20 = 100: 105 passes. B is verified 'sound' at R1's child (within the existing 80 cp margin of our best quiet move there, search.rs:3423) and S is played. The opponent simply plays R1 - their best reply - and we are 100 cp worse than the move we had. In Tier 1 the same S is played with no bound at all, because the design skips the declines search (DESIGN:68-69). Note the value needed for the fix is already computed: in Tier 1 the 'allows' group is every reply, so the step-3 group_look already returns min-over-all-replies, and the design discards it after using it only to pick B's verification position.
- **Suggestion:** Define soundness at the horizon as a minimax over ALL replies, not an existential over one: require, for every legal reply R, that our objective value after (S,R) - computed by the opponent-best search over all replies, not just decliners - is >= best_objective - 20. Use the Tier-1 step-3 value directly instead of skipping the bound. Keep B's verification only as an enabler that makes the sacrifice legal, never as the score. Report 'forced' only when the bound holds for all R and no R is a refutation.

## [BLOCKER] 'Verified sound' reuses the root look's near-equality thresholds at a child two plies deeper, at a small fraction of the budget, where the code itself says the look cannot tell sound from unsound
- **Where:** `DESIGN_brilliant_in_n.md:71-73,97-98 vs src/search.rs:3407-3424 (margin/veto/floor/enough),3411-3416 (the code's own admission)`
- **Claim:** The design never defines what 'sound' means at the horizon and borrows the root look's verdict, whose definition in code is 'within margin = b*b/125 (80 cp at Brilliance 100) of the best quiet move, and not below floor = 50-b (-50 cp), reached at depth da>=5 with the other group at db>=da-1' (search.rs:3407-3410,3423). Those thresholds are calibrated for a look that today runs at `look_depth = done_depth` on the whole look budget (search.rs:3334-3345); the horizon splits that same budget across K candidates x up to three group_looks, so each child verification is a few thousand nodes at depth 3-4, where an 80 cp tolerance is pure noise.
- **Failure:** go movetime 300, the design's own target (DESIGN:58). The existing look is ~43% of what the search used (BRILLIANCE_PCT 30, search.rs:3341-3342), i.e. ~100 ms; with K=4 candidates and three searches per candidate that is ~8 ms, a few thousand nodes. B = Bxh7+; the refutation is a zwischenzug with check at ply 8+ (...Qa5+, regaining the piece with tempo). The child search never reaches it, scores B at -20, and -20 >= floor(-50) and >= best_quiet-80, so B is 'sound'. The engine plays S, the opponent plays the zwischenzug, and we are a piece down. This is the same failure the code records as measured: at level 8 a depth-3 neutral look 'rejected the Greek gift', i.e. shallow neutral looks are known-unreliable (search.rs:3411-3416, may_veto = full). The design has no minimum-depth gate at the child, so the failure is systematic rather than exceptional.
- **Suggestion:** Carry the root look's depth requirement into the horizon explicitly: require the child verification to reach the same `enough` rule (search.rs:3410) before any verdict, and refuse to fire (and report 'incomplete', per DESIGN:77-78) when the split budget cannot reach it. Alternatively define horizon soundness as equality with the root-look predicate - neutral params, NeutralGuard, same margin/floor, same depth floor - and state that a candidate whose verification cannot reach that depth is rejected, not accepted.

## [BLOCKER] No info-string grammar is specified, and a new prefix silently hides the horizon move from the only parser
- **Where:** `DESIGN_brilliant_in_n.md:52-56, 88-89; testing/brilliance.py:93-95, 136-137, 145`
- **Claim:** The design requires the horizon look to 'announce a horizon finding' and 'report the depth actually reached' but never gives the line's grammar; the only consumer is testing/brilliance.py, which matches by prefix `info string brilliancy look` and by the literal suffix `-> played`, with no regex, so any new prefix (e.g. `info string horizon look:`) makes a horizon move invisible to the suite and any line under the shared prefix at Brilliance 0 fails 12 rows.
- **Failure:** Horizon look runs on control B6 (`2r3k1/5ppp/8/8/8/8/5PPP/1R4K1 w`, c3 g2g3) and plays a setup move, printing `info string horizon look: setup Ra1 N=2 -> played`. The parser's `look`/`played` lists only collect lines starting with `info string brilliancy look` (line 93), so `played` stays empty and the control check `ok = not played` (line 136) reports PASS for a deliberate swap the suite exists to catch. Conversely, if the implementer reuses the `brilliancy look` prefix and also logs a gated-off or incomplete horizon line, the Brilliance-0 branch `ok = best is not None and not look` (line 145) fails for B1/B2/B3/B4/B5/B6 x every level (12 rows today).
- **Suggestion:** Pin the grammar exactly: every horizon line must begin `info string brilliancy look: horizon ` and, when the move is taken, end with the bytes ` -> played` as the final token (no punctuation or diagnostics after it, because the test is `line.endswith("-> played")`). Emit nothing under that prefix at all when Brilliance == 0 or any listed gate is off. Add `horizon <uci> N=<n> replies=<k> allows=<a> declines=<d> tier=<forced|bait>` before the marker so a control can still carry a verdict line without the marker (B6 already prints one today: `info string brilliancy look: sacrifice ...` with look count 1).

## [BLOCKER] The FORCED tier announces a proof it does not have
- **Where:** `DESIGN_brilliant_in_n.md:31-47, 96-98; src/brilliant.rs:16-19`
- **Claim:** Tier 1 reports 'forced' on the strength of `declines is empty` plus one soundness check on the opponent's best allowing reply, but `allows` is only brilliant::candidates' static nomination, which the module doc says is not a judgement of soundness, so the word 'forced' asserts a verified brilliancy against replies that were never verified.
- **Failure:** Position where our quiet S is available and every one of the opponent's 30 replies statically leaves a piece hanging (candidates non-empty for all), but for 29 of them the neutral search would reject the sacrifice (as it already rejected the Greek gift at level 8, README:112). Tier 1 fires on the single best reply's verdict and the log says the brilliancy is forced against every defence; the engine plays S believing all replies lose material when in fact the opponent's second-best reply holds comfortably. This is exactly the case the user asked for ('if whatever the opponent does ... then try'), so a wrong 'forced' report is the one output that must never be wrong.
- **Suggestion:** Do not print `forced` unless every allowing reply's brilliancy was verified (a search each, which the design's own cost section does not budget). Otherwise report `tier=all-replies-allow (nominal)` and reserve the word 'forced' for a verified claim; the grammar should make this impossible to confuse: `tier=forced` only after all replies verified, `tier=bait` or `tier=nominal` otherwise.

## [BLOCKER] Horizon look's sub-searches get a repetition history missing the two setup plies, so a repetition draw is scored as a winning brilliancy
- **Where:** `src/search.rs:2455 (group_look hist), src/search.rs:1294-1315 (is_repetition), src/search.rs:1869 (push rep_key per ply); DESIGN_brilliant_in_n.md:54-72`
- **Claim:** The design roots each horizon-look search on the position after S,R and passes it the root's history unchanged, but group_look copies `hist` verbatim (`t.hashes = hist.to_vec()`, search.rs:2455) and never records the S and R plies, so every repetition test inside the look is offset by exactly two plies and a line that repeats a real game position is scored as a normal (winning) line instead of 0.
- **Failure:** N=2, main-search history H (root's own hash removed at search.rs:2749-2752, so H ends at the opponent's position P-1). The look builds P2 = R0+S+R_opp and calls `group_look(&ntt, &P2, &s.hashes, ...)`. group_look seeds `t.hashes = H`; when the sub-search descends to P3 it pushes rep_key(P2), so `is_repetition` (search.rs:1307-1312) compares P3 against `hashes[n-2] = H[len-1] = P-1` — a position two plies older than the correct `rep_key(R0)`. A line S, R_opp, B, ... that returns to R0 or P1 is therefore not scored as `draw_score`; the look reports B as 'verified sound', the opponent's actual drawing defence R_opp is scored as bad for them (inflating 'the worst declining value'), and Tier 1/2 plays S in a line that is a repetition draw. Under NeutralGuard CONTEMPT=0 (search.rs:2417), the missed draw even shows up as 0 rather than a signal, so nothing else flags it.
- **Suggestion:** Before each horizon-look call, build the history for the look's root explicitly: `hist = s.hashes + [rep_key(R0), rep_key(P1), ... for every setup ply actually played]`, using `rep_key` (not raw `board.hash()`) to match uci.rs:548/564. Unit-test with a 4-ply cycle so the look sees the draw. Do not rely on `s.hashes` alone; the design's cost section never mentions extending it.

## [BLOCKER] group_look cannot express a minimising worst-reply search
- **Where:** `src/search.rs:2439-2496 (group_look), 1745-1755, 2062-2078 (root max), design 63-79`
- **Claim:** group_look is a maximising, deepen-to-completion root search that returns only the best root score and its PV (search.rs:2062-2078, 2489-2495); it has no per-reply result and no score-based early exit, so the design's "one group_look over declines -> the worst declining value ... abandon as soon as any reply is worse" (design:67-69, 24-27) cannot be built from it, and the stated cost of "up to three searches per candidate" is wrong.
- **Failure:** A candidate S has 30 declining replies. Step 2 as specified deepens group_look to max_depth and returns the maximum over the whole group; the caller cannot see which replies were searched or what each scored, so there is no point at which it can "abandon as soon as any reply is worse". Either the look runs the full group (cost ~30 replies' worth of nodes, not the ~1 search the design budgets) or an implementer adds an ad-hoc break that leaves the group partial and silently reports a value for a set it did not search.
- **Suggestion:** Add a new free function next to sub_search (search.rs:2347), constructing Searcher(s) and calling the public search, with no change to Searcher::search or group_look. For step 2 test each reply R by searching the child board after S,R (our move) with the null window (T-1, T) where T = anchor - 20: a fail-high (>=T) proves v(R) >= T, a fail-low (<=T-1) means this reply is at least as bad as the threshold and the candidate is abandoned immediately. That is one cheap search per reply with the short-circuit the design asks for, and it replaces the group search rather than reusing it.

## [BLOCKER] The horizon look has no budget in a node-budgeted level; clock-scaled N does not exist at levels 1-18
- **Where:** `DESIGN_brilliant_in_n.md §"Horizon: clock-scaled, iteratively deepened" and §"Cost"; src/search.rs:2830-2870 (HEAD a2690d0); src/skill.rs:79-98`
- **Claim:** The design derives N (2, then 4, then 6) from the move's clock, but levels 1-18 have `nodes > 0` in skill.rs TABLE, so search_position_inner clamps `limits.nodes` and the level stops on that node count, never on the clock; measurable proof: level 1 given `go movetime 5000` returns `bestmove` in 15 ms having searched 294 nodes (Brilliance 0), identical to `go movetime 300`. `deep_mode` is `full && ...` (search.rs:2765) and DEEP_MIN_MS is only consulted inside it, so the design's ">4 s -> N=4" trigger is never evaluated at any weakened level. And "a slice of the move's budget" at level 1 is ~150 nodes, which cannot fund even one group_look: brilliant::MIN_LOOK_NODES is 96 for a single look and the existing weak-level look deliberately gets its own 30,000-node VERIFY_NODES precisely because the level's budget is too small (brilliant.rs:24-37, search.rs:2850-2858).
- **Failure:** At Skill Level 1 the horizon look either (a) takes 'its slice' of the level's 150-node budget, group_look returns a partial depth-1 score for the declines set (t.check_mask=3, brilliant-style budget under MIN_LOOK_NODES), and Tier 2 compares that garbage against `best - 20cp` -> the level's move is replaced on noise; or (b) it is given an independent budget, in which case at level 1 it spends up to 3 group_looks x K candidates x ~30k nodes ~= 375 ms (measured: one 30k-node verification costs ~25 ms at 1.1M nps), i.e. 25x the level's 15 ms whole search, and the level's documented 'move quickly whatever the clock' behaviour (skill.rs:9-13) and its measured Elo are gone.
- **Suggestion:** Do not reuse the immediate look's clock/percentage model for levels 1-18. Add a `brilliant::HORIZON_NODES` (node-priced, like VERIFY_NODES) and specify per level: horizon budget = clamp(k% of level.nodes, MIN_LOOK_NODES, MAX) with a hard floor check -- if the floor cannot be met, do not run at all. Concretely: gate the horizon look off for levels 1-12 (nodes <= 13,400: even 20% is under one usable verification), allow N=1 only at levels 13-16, N=2 at 17-18. At levels 19-20 (nodes == 0, time-driven) either keep it node-budgeted via an explicit node_limit on the look or gate it off entirely: a time-paid horizon look there reduces the level's own search depth, which is exactly what the 5.4.0 design avoided by paying the look in nodes at weak levels.

## [BLOCKER] Tier 1 ("declines is empty") is the typical case, not the forced one, and breaks the brilliance.py controls
- **Where:** `DESIGN_brilliant_in_n.md §"The rule" (Tier 1); src/brilliant.rs:88-111; testing/brilliance.py:93,143-144; tests/brilliance.epd`
- **Claim:** The design's forced test is `declines is empty`, i.e. every opponent reply still leaves a `brilliant::candidates` nominee. That predicate is nearly always true because `is_sacrifice` nominates any move that gives material away by SEE >= -150 or leaves 250+ hanging. I measured it with the real code: in the Greek-gift EPD (B4) 21 of 21 quiet non-sacrifice candidates have all 31 replies 'allowing' (declines empty); in control B5 3 of 5 quiet candidates fire Tier 1 (b1c1, b1d1, b1e1, all 20 replies); in control B6 2 of 16 fire (b1d1, b1e1); in B3 `d1e1` and `d1d6` fire alongside the required `d1d8`. Across children, '>=1 candidate' holds for 39/39 replies in a quiet opening and 20/20 in an equal rook ending. The design also never requires that S *created* the opportunity: Bxh7+ already exists before a2a3, so 'a brilliancy is available after S' is true for essentially every quiet S.
- **Failure:** testing/brilliance.py treats B5 and B6 as controls: the check is `ok = not played`, where `played` is any line starting `info string brilliancy look ... -> played` (brilliance.py:93,143-144). A Tier-1 fire for b1d1 or b1e1 in B5/B6 prints that line and fails the control; a Tier-1 fire for d1e1 in B3 makes the engine play d1e1 instead of d1d8 (`ok = best == c['bm']`) and fails B3. Since the suite runs levels [21,14,8,3,1], this breaks the 36-check hard invariant at the weak levels the design is aimed at. Separately, step 1 cannot early-exit for Tier 1 -- deciding `declines is empty` requires scanning every reply -- so the design's claim that 'the static scan early-exits ... so step 1 is cheap' is false for the forced tier (measured 5.4-6.5 us/child x 31-47 replies x K candidates).
- **Suggestion:** Require S to create the opportunity: B must NOT be in `brilliant::candidates(root)` (or, better, the verified value of B after S must exceed the neutral best-of-candidates value before S by the existing margin b*b/125). Also require S itself to be materially neutral (is_sacrifice(root, S) false and see(S) not below the existing floor) and require the allowing set to be filtered to replies that were not already forced/allowing before S. With that, declines is empty becomes a genuinely special case rather than the default. Until then, do not print `-> played` from the horizon look at all (use a distinct `info string horizon ...` prefix and extend the runner's parser), so a wrong Tier 1 cannot silently pass or fail the control contract.

## [BLOCKER] Tier 2 compares a neutral child score against the personality-inflated root score (up to 340 cp) inside a 20 cp tolerance
- **Where:** `DESIGN_brilliant_in_n.md §"The rule" (Tier 2: `value(normal best move) - 20cp`); src/search.rs:3361-3378 (HEAD); src/personality.rs:327`
- **Claim:** Tier 2's bound is `min over declining R' of value(after S,R') >= value(normal best move) - 20cp`. `value(after S,R')` comes from `group_look`, which the existing code runs under NeutralGuard with SacParams::neutral() and a fresh TT (search.rs:3379-3381). `value(normal best move)` is `best_score` from the main search, which still contains the sacrifice bonus `best_sb` -- SACRIFICE_BONUS = 340 cp at the default personality (personality.rs:327). The existing comparison deliberately uses `best_true = best_score - best_sb` (search.rs:3361) and says why: 'the personality's optimism about its own attacks is what makes a sacrifice unsound, so it must not judge it' (search.rs:3374-3378). Skill Levels never change the personality (skill.rs:24-25), so this full 340 cp bias is present at every level 1-20 -- the design's own target.
- **Failure:** A quiet setup S whose neutral value is, say, -120 while the level's best move has score +180 of which 340 is the sacrifice bonus (true objective -160): Tier 2 evaluates -120 >= -160 - 20 -> true and plays S, even though S is 40 cp worse than the objective best. In the opposite direction, a genuinely free setup S is rejected whenever the level's chosen move carries a large sacrifice bonus, so the bait never fires in exactly the attacking positions it is for. A 20 cp 'noise tolerance' cannot survive a 340 cp unit mismatch.
- **Suggestion:** Specify that every reference value in Tier 1/Tier 2 is the objective score: root best = `best_score - best_sb`, exactly as search.rs:3361 does, and the per-reply values are the neutral group_look scores with no bonus. If the horizon code cannot reliably know `best_sb` for the level's chosen line (it is `lines[i].sb` after skill::choose), the tier must not run at all rather than compare mixed units.

## [MAJOR] The static nominator counts plain blunders as 'a brilliancy is available', so 'declines is empty' and the FORCED tier are artifacts of a junk predicate, and the verified B need not be the candidate the partition counted
- **Where:** `DESIGN_brilliant_in_n.md:24-33,46-47 vs src/brilliant.rs:88-111, src/search.rs:472-485`
- **Claim:** `brilliant::candidates` nominates any move with `!see_ge(board, m, -150)` (gives away a minor or more) or any move after which `leaves_material_at(child, 250)` - i.e. anything that leaves a >=250-value piece winnable by SEE (a knight is 320, eval.rs:88). So 'a brilliancy is available' means 'some move gives material away', which is true in any sharp position even when every such move is a simple blunder. The partition (allows/declines) is then a partition on blunders, while the tier report and the 'forced' claim are about brilliancies. Separately, step 1 is an existential over candidates but step 4 verifies one B; the design never says which candidate is B when several are nominated, so the static set and the search verdict can be about different moves.
- **Failure:** After S and every opponent reply, the only nominated move is Nxf7 (SEE -320: a knight for a pawn, no follow-up). Statically every reply 'allows', so declines is empty and S is Tier 1 FORCED. B = Nxf7 goes to the neutral child comparison and scores -40: >= floor(-50) and within 80 of the best quiet move, so it is 'sound'. The engine plays S and reports 'forced' to the user while no brilliancy exists at all - the position merely had a piece hanging. A move that simply hangs one of our pieces (leaves_material_at(child, 250), search.rs:472-485) is indistinguishable in this pipeline from a Qxh7+ sacrifice.
- **Suggestion:** Make the availability test and the acceptance test the same predicate: nominate a candidate only if the neutral child search would rank it among the moves it actually prefers (i.e. the step-4 comparison, run per candidate), and drop candidates whose SEE loss exceeds a bound or whose neutral score is below the floor before the partition. When several candidates exist after a reply, define B deterministically (best neutral score among the nominated set) and report which one the tier claim is about.

## [MAJOR] group_look returns side-to-move scores; re-rooted at the child that is the opponent's frame, so the Tier-2 comparison as written inverts
- **Where:** `DESIGN_brilliant_in_n.md:38-40,66-72 vs src/search.rs:2453-2456,2479-2490`
- **Claim:** The design compares `min over declining R' of value(after S,R')` against `value(normal best move) - 20` without stating a frame. `group_look` builds its Searcher with `root_color = board.side_to_move()` (search.rs:2456) and returns `sc - sb` from that root (search.rs:2490) - a side-to-move score. Step 2's group_look is rooted at the position after S, where the side to move is the opponent, so its value is the opponent's score, not ours; the baseline is our score from the parent. Read literally, the inequality passes exactly when the position is good for the opponent.
- **Failure:** Our baseline `value(normal best move)` = +50. After S, the opponent's best declining reply leaves them at +40 in their own frame (we are -40). Literal implementation: is 40 >= 50-20 = 30? Yes - so S passes the no-regret test and is played, although by the correct inequality our value (-40) is 90 cp below the baseline and must be rejected. The bug is systematic in the dangerous direction: it accepts precisely the declines that are good for the opponent. The same ambiguity exists in step 3 ('their best allowing reply') and step 4's B-vs-quiet comparison, which are all re-rooted at children.
- **Suggestion:** State the frame for every quantity and negate child-rooted group_look results into the parent's perspective before comparing. Better: do not re-root - keep one perspective per comparison by evaluating `value(after S,R)` as the negation of the child search's minimax, and make the Tier-2 predicate a single expression all in our frame; add the frame to the 'info string' report so the sign is auditable.

## [MAJOR] Tier 2 compares an absolute subjective baseline (personality eval plus up to 340 cp of ply-2 sacrifice bonus) against neutral child values; the existing look deliberately never does this
- **Where:** `DESIGN_brilliant_in_n.md:38-40,9-11 vs src/search.rs:1696-1704,2062-2068,3361,3420-3423,3443`
- **Claim:** `best_score` is a subjective root score: it carries the personality evaluation (the look needs NeutralGuard to escape it, search.rs:3379,3404) and up to 340 cp of sacrifice bonus added at ply 2 when `stm == root_color` (search.rs:1696-1704, INITIAL.sac_bonus = 340, personality.rs:327). `root_best_sb` records only the ROOT move's bonus (search.rs:2062-2068), so ply-2 bonuses remain inside the score. The existing look therefore never compares a subjective absolute against a neutral one - it compares two neutral scores and only translates the difference onto the subjective scale (search.rs:3420-3423,3443, best_true at 3361). The design's `value(after S,R') >= value(normal best move) - 20` compares absolutes, and the design never says which SacParams/NeutralGuard each of its three searches runs under. Also, the design's premise misdescribes the code: it says '60% at ply 2' (DESIGN:9-11), but the code applies the FULL bonus at ply 2 (`self.sac.bonus`, and `max(bonus, chain)` when the root move was a sacrifice, search.rs:1698-1699); only ply 4 is halved.
- **Failure:** Step 2 runs with the level's own sac params (the natural reading, since the design only calls step 4 neutral). group_look re-roots at the child, so root_color is the opponent and the full 340 cp bonus lands on THEIR ply 0 and ply 2 (search.rs:1696-1704). The returned value is depressed by up to 340 cp, the no-regret test fails, and the feature never fires - contradicting DESIGN:58 ('go movetime 300: N = 2 almost always'). Run neutrally instead and the opposite happens: the baseline keeps its 340 cp and the child searches lose it, so S passes by up to 340 cp of pure scale error. Either choice changes the classification of the same S; the design gives no way to tell which it means.
- **Suggestion:** Specify for each of the three searches whether it uses NeutralGuard + SacParams::neutral(), and normalise the baseline into the same frame (compare neutral-to-neutral and translate the delta, as search.rs:3443 already does, or subtract the ply-2 bonus explicitly). Correct DESIGN:9-11 to say the ply-2 reward is full, not 60%, and price the horizon look against a baseline that already contains that full nudge.

## [MAJOR] The horizon gate list omits the existing look's score/mate fences, so an already-won position can be replaced by a slower setup
- **Where:** `DESIGN_brilliant_in_n.md:87-89 vs src/search.rs:3325-3328 (bril_ready),3374 (best_true.abs() < 1500),3422-3423 (sb2 >= MATE_BOUND / sa < 1000)`
- **Claim:** The design's gates are user_nodes, user_depth, MultiPV>1, ROOT_FILTER, Brilliance==0 and a vague 'forced/already decided'. The existing look additionally refuses to run when `best_score.abs() >= MATE_BOUND` (search.rs:3327-3328), when `best_true.abs() >= 1500` (search.rs:3374) and when `sa >= 1000` (search.rs:3423), and its take predicate treats any mate-scored sacrifice as sound unconditionally (`sb2 >= MATE_BOUND`, search.rs:3422). None of these are carried over, and the design's Tier-2 arithmetic uses raw scores, which for mate scores are MATE-ply encodings.
- **Failure:** Root has Qh7 mate in 1 (best_score ~ MATE-1); a SEE-losing check S also exists. Statically all replies after S allow a candidate, so Tier 1 fires. B's verification reaches a mate score, and the existing predicate accepts `sb2 >= MATE_BOUND` with no margin. The horizon plays S - a setup that mates in 2 or 3 - instead of the mate in 1, because `value(normal best move) - 20` is compared as a mate-distance integer and the setup's child value is also a mate score. The three fences above exist precisely to keep the look out of decided positions; removing them turns a 'brilliant' filter into a move-weakening one in won positions.
- **Suggestion:** Carry `bril_ready`'s mate bound and `best_true.abs() < 1500` into the horizon gate verbatim, require `sa < 1000` at the child, and exclude mate-scored positions from the Tier-1/Tier-2 arithmetic (treat any mate score as 'already decided: play the main search's move').

## [MAJOR] Budget exhaustion cannot be reported from group_look's return value, and N is not its depth
- **Where:** `DESIGN_brilliant_in_n.md:52-56, 75-79; src/search.rs:2439-2495, 3405`
- **Claim:** The design says to 'report the depth actually reached, the way the main search reports done_depth', but group_look returns `Option<(i32,i32,i32,Vec<Move>)>` with None when no iteration completed (src/search.rs:2475-2495), the caller silently skips on None (`if let (Some(..), Some(..))` at 3405), `done_depth` is never emitted as a field anywhere, and its returned `depth` is the verification search depth, not the horizon N.

Concretely, make Tier 2's replacement conditional on `full` (mirroring `may_veto`), and at weak levels route the horizon result into the MultiPV line list as an extra scored candidate that skill::choose may pick -- so the choice stays inside the calibrated cp-loss allowance. Tier 1 may likewise only report at weak levels.

## [MAJOR] Replacing the chosen move after skill::choose bypasses the cp-loss allowance accounting
- **Where:** `DESIGN_brilliant_in_n.md §"Cost"/§Gates; src/search.rs:3223-3247 (HEAD); src/skill.rs:246-276`
- **Claim:** The design never says where in the pipeline the horizon look runs, only that it 'plays S'. The natural slot (where the existing brilliancy look sits, search.rs:3329) is *after* `skill::choose`, which has already charged the level's mistake allowance for a different move: `let loss = (best - lines[pick].score).max(0); let left = (budget - loss + lvl.cp_loss)...; BUDGET.store(left)` (skill.rs:272-275). If the horizon look then swaps best_move to S, the recorded payout is for a move that was not played, and S is played without any charge against the allowance. The existing look rarely triggers (it needs a root brilliancy candidate and `bril_ready`), so the leak is small today; per finding 2 the horizon Tier 1 would fire on ordinary quiet moves, making the leak the common path.
- **Failure:** Level 3 (cp_loss 140, max_budget 600): the level chooses a move 120 cp down and is charged 120; the horizon look then replaces it with a move whose true loss is 0. Over a game the allowance drifts upward relative to the calibrated stochastic process, so the level's realised average loss per move falls well below `cp_loss` (skill.rs:14-19 defines that average as the calibration), i.e. the horizon look silently strengthens the level.
- **Suggestion:** Place the horizon look before skill::choose: append S to `lines` with the neutral look's objective score (loss measured from `best - best_sb`), so skill::choose prices it like any other candidate. If it must run after, it has to re-run the allowance arithmetic for S (charge `(best_true - value(S)).max(0)`) before setting best_move. State this explicitly in the design.
